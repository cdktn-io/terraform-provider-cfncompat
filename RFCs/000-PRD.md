## 1. TL;DR

AWS CDK's most valuable asset is its **L2 construct library** and the L3 patterns built on top — service-integration patterns, secure-by-default wiring, and higher-level solution constructs that encode AWS expertise. Today that asset is **locked to a single output format: CloudFormation.** A large and growing population of customers cannot consume it because they deploy with **Terraform or OpenTofu** (and increasingly Pulumi) and run their entire platform — state, policy, approval, drift — around that engine.

This PRD is focused on better Terraform/OpenTofu support. The first-class, concrete deliverable is **Terraform/OpenTofu support for AWS CDK** — pulumi or other engines are not the focus of this PRD. The key design insight is *how* to deliver it sustainably: the real gap is **not** "add a Terraform exporter" (see prior attempts to bolt one on section 6). The real gap is that **CDK's synthesis output is hard-wired to CloudFormation**, so its construct library can only reach one engine. We aim to deliver better TF/OTF support by abstracting CDK's CloudFormation-specific output behind an interface (the existing CFN behavior becomes the default implementation) and **CDK Terrain (https://cdktn.io) implements the Terraform/OpenTofu backend** against it. A welcome side effect of doing it this way rather than as a one-off TF exporter: the seam is generic, so **Pulumi or any other engine** can later implement its own backend too — TF support as a primary goal of this PRD, ecosystem reach as a stretch goal.

**The ask:** commit to an **RFC for the synthesis-backend interface** primary implementation provided in CDK Terrain this cycle.

**Why AWS should care:** the same L2/L3 library reaches every IaC engine's pipeline → more developer mindshare, more customer stories AWS Solutions Architects can land, and direct relevance to AWS's intent-level / "AWS Blocks" direction — **without any new dependencies for existing AWSCK>CloudFormation users.**

## 2. Problem statement & "why now"

AWS may recognizes **"better Terraform support"** as a driver. The four forces below are *why* that matters now and *who* it's for — and they explain why the durable answer is a synthesis seam rather than another bolt-on exporter.

CDK assumes CloudFormation end-to-end. For a customer whose platform runs on Terraform/OpenTofu, adopting CDK means potentially introducing a new deployment engine (requiring buy-in from platform team and higher up), hanlding a new state model, policy/approval tooling, and team skills — often a significant hurdle. So they forgo CDK's L2/L3 ergonomics and hand-author verbose HCL or wrangle hard-to-compose modules instead.

Four forces make this urgent for the 2026 cycle:

1. **Enterprise Terraform/OpenTofu mandates.** Large orgs have standardized on TF/OpenTofu state + workflow. They want CDK's L2 ergonomics **inside the pipeline they already run**, not a parallel CFN pipeline.
2. **Single multi-tool workflow.** Platform teams want one `plan`/`apply`/state model across AWS *and* non-AWS resources (DataDog, CoudFlare, Vendor PAM Solutions, ... ), with CDK authoring the AWS portions — not two deployment planes to reconcile.
3. **L2 ergonomics for Terraform users.** TF/CDKTN users lack high-level constructs (Grants, Connections, secure defaults, solution constructs). The value AWS already built is simply unreachable to them.
4. **The AI inflection (the marquee driver).** AI-assisted infra works best with **higher-level building blocks that express intent**, not exhaustive declarative L1 configuration with edge-case combinations. As of mid-2026, enterprise AI budgets are being burned generating **verbose, non-deterministic HCL** and stitching brittle, hard-to-extend modules — which doesn't scale. Well-tested, composable, intent-level component libraries (CDK **L2→L3**) are the right substrate for AI-era infrastructure. This is reinforced by initiatives like **"AWS Blocks"** (an open-source library for composable AWS backends): the demand is precisely for **higher-level, well-tested components that land in existing Terraform/OpenTofu platform pipelines.** CDK already *has* that component library — it just can't reach those pipelines.

**Net:** the constraint is an architectural coupling inside CDK, and the cost of that coupling is rising fastest exactly where AWS wants to win (AI-assisted, platform-standardized enterprises).

## 3. Customers & personas

| Persona | Today's pain | What success looks like |
|---|---|---|
| **Platform/IaC team at a TF-standardized enterprise** | Can't adopt CDK; CFN is a second deployment plane they won't run | Author AWS resources with CDK L2/L3, emit `tf.json`, deploy through their existing TF/OpenTofu pipeline & state |
| **CDK developer blocked by an org TF mandate** | Knows CDK, forced into HCL by org policy | Keep CDK authoring; output targets the org's engine |
| **AI-assisted infra team** | AI generates verbose, non-deterministic, edge-case-fragile HCL; budget + reliability blow up | AI emits intent-level CDK L2/L3; deterministic, tested constructs render to the target engine |
| **AWS Solutions Architect / "AWS Blocks" author** | Reference solutions only ship as CFN/CDK-CFN, missing TF-shop customers | One construct library, many engines → more landable customer stories |
| **Alternative-engine ecosystem (e.g. Pulumi)** | No path to reuse CDK's L2 intent | Implement the same public seam; reuse CDK's construct library |

## 4. Goals & non-goals

**Goals**
- Let the **same CDK L2/L3 construct code** synthesize to a non-CloudFormation engine (Terraform/OpenTofu first) **without a second construct library**.
- Keep a **single L2 codebase** — no fork, no per-service re-implementation.
- **Zero impact on CloudFormation users**: no new dependency, no behavior change, byte-identical templates.
- Make the seam **generic** — any synthesis backend (CDK Terrain, Pulumi, …) can implement it; AWS does not pick a winner.
- **Runtime-agnostic**: the output is consumed by Terraform *or* OpenTofu; AWS takes no position in that ecosystem split.

**Non-goals (explicit, to keep AWS un-locked-in)**
- AWS does **not** build or own a high-level construct library for non-AWS providers.
- AWS does **not** (initially) own the Terraform/OpenTofu **CLI, deploy, or state** experience — that's the backend implementer's and/or native tooling's job.
- AWS does **not** choose Terraform vs OpenTofu, nor take on HashiCorp/IBM ecosystem politics.
- **Not** 100% L2 coverage on day one — value lands incrementally, module by module.
- CloudFormation-only **platform** features (macros, `Fn::Transform`, nested-stack semantics) are **not** promised on other engines.

## 5. The capability-gap taxonomy (what we're actually solving for)

Below is an engine-agnostic catalogue of where CDK's CloudFormation assumptions meet a non-CFN target, each framed as a **problem with severity** — not a solution. (Grounded in a source-level study of `aws-cdk-lib`; The follow-on RFC decides *how* each is addressed.)

| # | Gap | What it means | Severity | Solvable in the seam? |
|---|---|---|---|---|
| G1 | **Output format is hard-wired** | Synthesis emits the CFN template shape + a CFN manifest artifact; the format is implicit, not a choice | High | **Yes** — the central seam |
| G2 | **Reference/value model is CFN-shaped** | Cross-resource references resolve to CFN intrinsics (`Ref`/`GetAtt`/`Fn::Join`) rather than the target engine's native interpolation | High (keystone) | **Yes** — proven feasible (appendix) |
| G3 | **Intrinsic-function parity** | `Fn.*` and pseudo-params map mostly 1:1 to engine functions; a few (e.g. **CIDR/subnet math**, certain lookups) differ or need a helper | Medium | **Mostly** — most map directly; a small set needs a polyfill helper |
| G4 | **Platform side-effects (custom resources)** | Some constructs rely on CloudFormation's custom-resource Lambda protocol for non-CRUD actions | Medium–High | **Partly** — many *evaporate* on a Cloud-Control-aligned provider; a residual set needs a polyfill |
| G5 | **Cross-stack & deploy/state model** | CFN exports/imports, deploy orchestration, and rollback are CFN-service semantics; TF/OpenTofu use state + plan/apply | High | **No (out of seam)** — different runtime model; backend/native tooling owns it |
| G6 | **Assets & bootstrap** | Lambda/Docker assets assume a CFN bootstrap bucket + change-set deploy | Medium | **Partly** — staging is reusable; delivery shifts to the engine |
| G7 | **The maintenance gap** | Prior approaches each fail a different way (see §6) — the real problem is *sustainably* reaching another engine without forking | High | **Yes** — the seam + a schema-aligned L1 target is what makes it sustainable |

**Reading of the taxonomy:** G1–G3 are squarely solvable behind a synthesis seam and are where the leverage is. G4/G6 are partly solvable and partly belong to the backend implementer. **G5 is honestly out of scope for a synthesis seam** — it's a deployment-engine/runtime-model difference, not a rendering difference, and the PRD should not pretend otherwise.

## 6. Why existing approaches don't close the gap

| Approach | Why it falls short |
|---|---|
| **Post-synth CFN→TF translation** (the old CDKTF "adapter") | Late-binding loses information available at construct time; breaks on intrinsics, conditions, macros. Lossy. |
| **A separate L2 library for Terraform** (e.g. TerraConstructs) | **Proven the mechanism works**, but at unsustainable cost: it forks the entire L2 layer onto a different provider whose resource shapes **diverge from CloudFormation** (one S3 bucket becomes *nine* Terraform resources), so nothing is shared with AWS CDK and coverage permanently lags. Empirical evidence this is the wrong cost structure. |
| **Hand-written HCL / Terraform modules** | No L2 ergonomics; in the AI era this is the verbose, non-deterministic, hard-to-compose output that is **blowing budgets** (driver #4). |
| **Full CDKTF** | Deprecated upstream; a separate framework, not CDK's construct library. |

The lesson from the strongest prior art (TerraConstructs): the **mechanism is feasible** (references *can* resolve to native interpolation), but the **only sustainable shape** is a single L2 codebase rendering to a **schema-aligned L1 target** — which is what an in-CDK seam + a Cloud-Control-derived provider makes possible.

## 7. Strategic options — how deep does AWS go?

Four ownership levels (the spectrum AWS leadership decides among):

1. **AWS ships only the interface seam.** Existing CFN behavior becomes the default implementation; third parties implement other backends. *Lowest cost, cleanest boundary.*
2. **AWS owns a Terraform synthesizer**, delegating deploy to native TF/OpenTofu or a partner.
3. **AWS expands the CDK CLI with a plugin system**; backends (e.g. CDK Terrain) become plugins.
4. **AWS fully owns the integration**, including CLI and deploy.

### Recommendation: **Option 1** — deliver Terraform/OpenTofu support *via* a generic, pluggable synthesis seam.

This directly satisfies the internal **"better TF support"** goal: Terraform/OpenTofu is the concrete Phase-1 deliverable. Choosing the *seam* form (rather than a one-off TF exporter) is what makes that support **durable, single-codebase, and zero-risk to CFN** — and incidentally extensible to other engines later.

- **AWS owns the seam, nothing engine-specific.** The CFN path is refactored to be the default implementation of the new interface — so CloudFormation users get **zero new dependencies and zero behavior change** (enforceable by a byte-identical-template CI gate).
- **CDK Terrain implements the Terraform/OpenTofu backend.** AWS never owns non-AWS construct code or the TF CLI.
- **The seam is not Terraform-specific.** Because it's a generic "render this construct tree to a target," **Pulumi or any other engine can implement its own backend** against the same public interface. AWS builds *one* thing and unlocks the whole IaC ecosystem.
- **Deeper options (2–4) become later phases** if adoption warrants — explicitly *not* required now.

**Why this is the right depth for AWS:**
- **Mindshare & reach:** the L2/L3 library — service-integration patterns, enterprise solution patterns — becomes consumable by Terraform/OpenTofu/Pulumi shops. AWS SA teams and "AWS Blocks" authors can land **more customer stories** with the components they already maintain.
- **AI leverage:** intent-level constructs are the substrate AI-assisted infra needs; freeing them from CFN-only output multiplies their addressable surface right as that demand peaks.
- **Strategic optionality at minimal cost:** one interface; the ecosystem does the per-engine work.
- **No downside for the core business:** CloudFormation remains the default and is untouched.

## 8. Success metrics / outcomes

- **Suggested PoC:** the *same* `aws-iam` construct code emits **byte-identical CloudFormation** *and* valid Terraform/OpenTofu config; a TF user deploys it through their own pipeline. (Proves G1–G3 + the keystone end-to-end.)
- **Adoption:** # of teams/orgs authoring AWS resources in CDK and deploying via TF/OpenTofu; CDK installs attributable to TF-shop users.
- **Coverage:** % of L2 modules reachable on a non-CFN backend over time (incremental).
- **Ecosystem signal:** ≥1 additional backend implementer (e.g. Pulumi) engaging the public interface.
- **SA / "AWS Blocks" leverage:** # of reference solutions now landable in TF/OpenTofu pipelines from the existing library.
- **Guardrail metric:** zero regressions / zero template diffs for existing CloudFormation users.

---

## 9. Scope & phasing

- **Phase 0 — RFC:** define the public synthesis-backend interface (the *what* AWS commits to; the *how* in `002-architecture.md` is input, not gospel).
- **Phase 1 — PoC:** `aws-iam` (foundational, no custom resources), single concrete-environment stack, Terraform/OpenTofu target. Proves G1–G3.
- **Phase 2+:** expand modules (S3, KMS, Lambda, Step Functions…), tackle assets (G6) and the residual custom-resource set (G4) via a backend-owned polyfill.
- **Explicitly out of scope (G5 + platform-only):** cross-stack export/import locking, nested-stack semantics, CFN macros/`Fn::Transform`, and the deploy/state runtime model. These are engine/runtime concerns, owned by the backend and native tooling — called out so the plan stays honest.

---

## 10. Risks & open questions

- **Cloud-assembly extensibility (for AWS):** can the cloud-assembly manifest carry a non-CFN artifact type, or does the CLI need a plugin path? (Decides how the backend integrates.)
- **Provider schema parity:** the Terraform/OpenTofu AWS Cloud-Control provider tracks AWS schemas on its own cadence; coverage is generally additive but version-dependent. Bounds backend coverage, not the AWS interface.
- **Runtime-model gaps (G5):** cross-stack locking and deploy semantics have no clean equivalent — set expectations explicitly.
- **Custom-resource residual (G4):** needs a backend-owned polyfill provider; a working blueprint exists in prior art.
- **Governance:** JSII multi-language safety and API-surface review for any new public interface (kept intentionally minimal).

---

## 11. The ask

For this planning cycle:

1. **Commit to an RFC** for the AWS CDK **synthesis-backend interface** — AWS owns *only* the seam, with the CloudFormation path as its default implementation and a zero-diff guarantee for existing users.
2. **A scoped PoC** (`aws-iam`) from **CDK Terrain** to prove G1–G3 end-to-end and validate the interface shape.

**What AWS commits:** the interface RFC + review; the byte-identical-CFN guarantee.
**What CDK Terrain commits:** the Terraform/OpenTofu backend implementation, the schema-aligned L1 rendering, the polyfill provider, and the PoC build.
**What this buys AWS:** the L2/L3 library reaches every major IaC engine, more landable customer/SA stories, AI-era relevance — with no risk to CloudFormation.
